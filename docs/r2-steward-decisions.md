# R2：管家对话入口

状态：grill-with-docs 访谈完成；Q1—Q21、配套规则和验收路径已整体确认，规格已发布为 [Spec R2 #18](https://github.com/kassol/AgentAnywhere/issues/18)。R2 尚未实现。

## 背景

R1 已完成发布与端到端验收；所有者简单使用后未发现具体问题，本轮以既有验收结果为基线推进 R2。R1 能力及证据见 [R1-14](evidence/r1-14.md)。

## 逐项决定

| 问题 | 已确认决定 |
| --- | --- |
| Q1 核心交付 | 管家对话入口：通过对话澄清目标、发起调研、查询进度和继续已有工作，复用当前执行能力。 |
| Q2 对话组织 | 多段独立管家对话，可新建和重开历史；每段可关联多项工作，话题分别保存。 |
| Q3 开始执行 | 明确委托且目标足够清楚时直接创建并执行工作；关键缺项先提问，普通讨论保持对话。 |
| Q4 操作入口 | 管家作为首页；保留工作列表、直接创建和工作详情操作。 |
| Q5 上下文范围 | 默认使用当前管家对话；根据用户要求按需查历史工作与报告，其他管家对话内容不自动带入。 |
| Q6 操作范围 | 在用户指令与目标工作明确时，覆盖现有创建、查询、追加、回答、取消、重试及完成后修改；以服务端回执为事实。 |
| Q7 后台通知 | 关联工作完成、失败或需要回答时自动回传关键状态卡；详细执行过程留在工作详情。 |
| Q8 回答与调研 | 管家直接讨论和解读已有报告；需要新搜索或网页正文时创建可追踪的调研工作。 |
| Q9 多项委托 | 同一消息可创建多项独立工作，关联到同一管家对话；沿用单并发排队，不引入父任务与自动汇总。 |
| Q10 模型选择 | 用户配置管家模型并维护允许使用的模型池；每项调研工作的模型由管家决定，无需逐项手选；候选模型、选择倾向与失败处理分别见 Q11—Q13。 |
| Q11 候选模型 | 管家仅从用户人工选定的模型池中选择调研模型，不自动启用网关中的其他模型。 |
| Q12 选择倾向 | 结果质量优先，基于可信能力资料，并参考已有实际验证；未实测模型按 Q20 处理，不根据名称臆测能力。 |
| Q13 模型失败 | 持续失败时停止并保留记录、进度，建议替代模型；收到明确重试指令后再创建新 Run。 |
| Q14 停止回复 | 停止本轮管家回复和后续派发，已创建的工作继续运行；取消工作需要明确指令或工作卡按钮。 |
| Q15 长对话 | 接近模型上下文上限时自动生成可见摘要，保留原文可查；工作状态实时查询。 |
| Q16 每轮上限 | 管家每轮最多 5 分钟、8 次模型调用、创建 3 项工作；触顶等待明确继续。调研 Run 仍沿用 45 分钟、40 次调用上限。 |
| Q17 报告追问 | 解释、摘要在管家对话内完成；明确修改或保存新版报告时创建新 Run，含糊时先问。 |
| Q18 全局待办 | 导航显示全局待回答数量并链接到相应工作；当前管家对话只接收自身关联工作的状态卡。 |
| Q19 对话并发 | 同时仅生成一轮管家回复，其他对话排队；管家与调研使用独立执行名额，调研沿用单项执行。 |
| Q20 未实测模型 | 人工入池、运行参数完整且有工具支持依据的模型可被选择；标注尚未实测，失败按既定规则处理。 |
| Q21 状态卡投递 | 工作状态投递到所有明确关联的管家对话，各对话引用同一工作与 Interaction；全局待办按问题去重。 |

## 已确认的整体定义

### 交付路径

新建管家对话 → 普通问题直接讨论 → 明确调研目标后从人工模型池选择模型并创建工作 → 返回工作卡、模型和简短选择依据 → 工作执行期间仍可与管家交流 → 关键状态返回所有关联对话，问题进入全局待办 → 用户在管家或工作详情回答、追加或取消 → 解读已交付报告，明确改稿时创建原 Task 下的新 Run。

一条消息可创建多项独立工作。各工作有自己的状态和成果，R2 不建立父任务，不自动汇总多个报告；用户明确请求比较已有报告时，管家可以读取并回答。

### 配套规则

- 管家仅调用受限的工作查询与操作能力；不获得宿主 shell、数据库管理、Sandbox 管理或外部账号权限。普通对话不创建 Worker Sandbox，也不占调研执行名额。
- 管家回复流式显示，并保存用户消息、管家回复、操作结果与关联工作。页面刷新或关闭不取消已接收的轮次；服务中断时明确标记中断，用户继续后核对已有回执，不重复创建工作。
- 指令涉及已有工作时，先确定目标。唯一明确指代可以直接执行；存在多个合理目标时提问。用户明确引用或操作历史工作后，将其关联到当前管家对话；仅浏览搜索候选不自动关联。一项工作可以被多段管家对话引用，状态及 Interaction 仍是同一份事实。
- 同一提问无论从工作详情还是管家回答，都只完成一次；并发回答、重复点击和重连以服务端事实为准。管家不能把模型生成的“已完成”文本当作执行回执。
- 模型池为空或没有满足运行要求的候选时说明缺项并停止派发，不自动启用池外模型。工作显示选定模型及选择理由；能力目录是选择依据，不承诺质量排名已实测。已有 Run 的模型保持固定；采用替代模型必须创建关联的新 Run，保留旧记录与进度。
- 管家默认使用用户配置的模型及其协议，复用现有 ModelConnection；工作使用模型池中模型的既有协议和有效参数。管家和调研均支持现有双协议。配置变更用于后续新轮次和新 Run，不改变在途请求。
- 自动摘要保留用户目标、已确认约束、工作引用和待处理事项；展示摘要及其覆盖范围，保留原消息可查。摘要失败时提示并停止本轮，不默默删除历史。摘要调用计入管家轮次预算；任务状态和成果内容通过查询取得。
- 管家 5 分钟按活跃执行计算，排队和等待用户输入不计时；回复结束、提问或触顶后释放管家执行名额。达到管家上限时保存本轮已有回复与操作结果，展示触顶原因；用户明确继续后才获得下一轮预算，已有工作和已成功操作不重放。停止尚未开始的管家轮次会取消其排队；取消管家回复立即停止后续工具派发，已经接受的工作操作如实显示。
- 沿用中文、键盘操作、HTTPS/WSS、服务端凭证和成果访问保护；不把第三方网页或报告中的文字当作用户的操作授权。

### 后续阶段

整体定义已经形成 [Spec R2 #18](https://github.com/kassol/AgentAnywhere/issues/18)，仓库副本见 [R2 规格](r2-steward-spec.md)。下一阶段由 to-tickets 拆分纵向任务及原生阻塞关系，再逐票实施。规格发布不表示 R2 已实现。

## R2 验收路径

1. 普通问答可持续对话且没有新 Task/Sandbox；刷新后历史与回复恢复。
2. 一段对话明确提出两项调研，创建两项独立工作并按现有队列顺序执行；每项可见模型选择和真实状态。
3. 目标缺项或工作指代有歧义时先问；无可用候选模型时明确提示。
4. 通过管家完成追加、回答、取消、失败重试及报告修改；与工作详情操作同一份事实。
5. 完成、失败、提问及额度等待返回全部关联对话，状态卡与全局待办去重且可定位；解读报告不自动产生新版本。
6. 停止管家回复、刷新、断线、重复提交和服务中断均不重复已接受的操作；已创建工作按既定规则继续。
7. 管家串行排队、排队取消、调研独立执行、额度触顶与长上下文摘要可控复现；摘要失败和模型持续故障有明确反馈，原文、工作和成果保留。
8. 通过真实模型双协议及 ego-browser 验证主流程；内部状态、队列和 Sandbox 保持真实，外部 HTTP 边界用于稳定复现异常。

## 当前源码事实

这些事实限定设计改造范围，不能视为 R2 已实现：

- `src/work.ts:37` 当前 Thread 强制绑定 Task；`src/work.ts:79` 消息只允许 user 角色。需要独立管家对话与管家回复的持久化。
- `src/work.ts:233` 起的工作创建事务同时建立 Task、Thread、Run 和首条消息并入队。先讨论后创建工作需要独立入口。
- `src/server.ts:248` 起已有取消、回答、创建、继续、重试和追加入口，优先复用其业务行为。
- `src/server.ts:157` 起的内部模型代理绑定 Run/epoch/token；当前实际 Pi 执行位于 Sandbox，独立管家轮次需建立受限的模型调用与操作边界。

## 范围边界

R2 不包含父子任务拆分、自动多 Agent 汇总、开发执行、账号写入、交互式浏览器接管、定时自动化、跨管家对话自动记忆和对话删除/归档管理。现有工作列表、直接创建、模型设置及工作详情继续可用。完整产品方向仍见 PRD/MVP。
