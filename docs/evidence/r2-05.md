对应 Issue #23，实现与隔离运行版本：`6f50f88b2f0fa68a541f1c65413e5cab6623d21e`。验证日期：2026-09-19。

## 实现与复核

当前用户原文先冻结控制类型、查询范围及追加内容；读取候选后，只能绑定该控制查询的唯一结果。候选文字不能改变目标或借用其他已关联工作。服务端固定 Task 与实际 Run，复用原入口的追加和取消业务事务，将业务写入、关联与操作回执一并提交。

跨轮继续核对同一操作身份。已接受操作只返回旧回执；未执行操作沿用原 Run，已有替换 Run 时拒绝执行。停止和重启保留已接受结果。UI 分别展示“已接收，等待安全时机”和实际消息状态“已应用”，不以模型文本推断生效。

独立 Spec 复核及主线程 Standards/调用链复查通过。定向公开 API 回归：Steward 7/7、107 次断言，Work 1/1、105 次断言；typecheck、build、diff-check 通过。恶意候选回归使用公开 API 创建可取消的 queued 目标，验证无法改选另一项已关联工作；没有直接 SQL 注入业务状态。

## 真实执行链路

在 cc-la 隔离入口执行：

```sh
node /opt/agentanywhere-r1/build-6f50f88b2f0fa68a541f1c65413e5cab6623d21e/infra/r1/test-steward-control.mjs
```

PostgreSQL、pg-boss、Pi 和 OpenSandbox 均保持真实，只有外部模型 HTTP 可控。

- 正在流式输出时，通过管家追加原文要求。回执先为 pending，原工作随后在安全时机应用一次；最终报告含 `STEERING_MARKER_12`，API 的 messageStatus 为 applied。
- Chat Completions 与 Responses 管家分别取消正在执行的调研；指定 Run 进入 cancelled，模型流断开，Sandbox SDK 确认没有活动沙箱。
- 取消业务已提交但最终回复仍挂起时，SIGKILL 隔离 Web 后重新启动。原轮显示 interrupted，已接受回执保留。
- 同一 Task 通过原 API 创建第三个 Run，再明确恢复旧取消回执。旧回执仍指向第二个 Run；第三个 Run 保持 running，未出现取消事件。随后通过 R1 直接取消入口清理第三个 Run。
- 两个同名候选不会被猜测取消；直接取消入口完成两项测试工作的清理。
